# 第五阶段：接口选择、轻量轨迹与失败报告

验收日期：2026-09-21。

## 阶段目标

本阶段集中修复真实使用中最影响可信度的三个问题：模糊目标选错接口、轻量模式轨迹表达含糊、失败任务没有完整报告。改动仍保持单用户轻量定位，不引入新的中间件。

## 1. 让接口选择先经过确定性候选排序

旧实现只有在目标完整包含 path、operationId 或完整 summary 时才加分。中文目标“查询最新帖子列表”既不包含英文路径，也不完整包含“分页获取帖子”，导致大量接口同分为 0；随后按路径排序截取 Top-K，`/api/posts` 被排除，模型只能在错误候选中选择 `/api/bookmarks`。

现在由 Java 先按以下证据排序，再把有限候选交给模型：

- 精确路径、operationId、完整摘要匹配；
- 中英文业务词匹配，并过滤“查询、接口、数据”等泛化词；
- GET/POST 等读写意图；
- 列表与详情形态，例如是否包含路径变量；
- 稳定的分数、匹配词和排序原因，随事件和报告持久化。

模型提示同时明确：候选已按相关性排序，泛化列表目标优先无路径变量的 GET，除非目标明确要求，不得用“收藏、我的、管理”等受限子资源替代目标资源。

### 同一目标的修复前后

目标均为“查询最新帖子列表，验证接口返回 200，并检查响应中包含帖子列表数据”。

| 版本 | 首选接口 | 结果 | 模型 Tokens |
| --- | --- | --- | ---: |
| 修复前 | `GET /api/bookmarks` | 断言失败 | 4,178 |
| 修复后 | `GET /api/posts`，候选分 45 | 1/1 步骤通过 | 3,350 |

修复后任务 ID 为 `2101925625186070531`，模型规划耗时 2,362 ms，HTTP 工具耗时 275 ms，报告生成耗时 56 ms。候选阶段保留 9 个相关接口及其 13 个关联 Schema。

Tokens 比该修复前样本减少 828，约 19.8%。这里只记录同一环境下的两次本机样本，用来证明 Prompt 输入收敛，不把它表述为稳定性能提升或通用准确率。

## 2. 让轻量模式的轨迹准确表达实际工作

轻量模式不再调用业务文档检索后返回“0 条证据”。任务轨迹现在明确拆成三个阶段：

1. `DOCUMENT_EVIDENCE_RETRIEVED`：显示“轻量模式未启用业务文档检索”；
2. `OPENAPI_CANDIDATES_SELECTED`：显示候选数量、首选接口、分数、匹配词和排序原因；
3. `SCHEMA_CONTEXT_READY`：显示候选接口数与关联 Schema 数量。

这样用户能区分“业务文档检索被关闭”和“系统没有任何规划依据”。计划依据来自 OpenAPI 候选与 Schema 闭包，报告中也保留相同证据。

## 3. 让失败任务也形成可审计报告

任务在规划、执行或观察阶段失败后，会先写入终态，再生成失败报告。报告生成失败不会覆盖原始错误。失败报告支持两类情况：

- 尚未执行 HTTP：`executionId` 可为空，保留终止阶段、错误码、错误消息、OpenAPI 候选与 Schema 指标；
- 已执行 HTTP：额外保留步骤状态、脱敏请求响应、断言实际值与预期值。

JUnit XML 对“规划阶段失败且没有 HTTP 步骤”的情况生成一个合成失败用例，避免导出一个看似通过的空测试集。

### 真实失败报告验收

使用目标“调用 GET /api/posts，并验证 HTTP 状态码为 418”制造安全的只读断言失败：

| 项目 | 结果 |
| --- | --- |
| 任务 ID | `2101926697971593217` |
| 计划 | 1 步，`GET /api/posts` |
| 实际响应 | HTTP 200 |
| 期望响应 | HTTP 418 |
| 任务结果 | 失败，0/1 通过 |
| 终止上下文 | `OBSERVING` / `AGENT_400_002` |
| 报告证据 | 9 个 OpenAPI 候选、脱敏请求响应、失败断言、Markdown 与 JUnit XML 导出入口 |

页面能够直接看到“状态码不符合预期”，以及 actual `200`、expected `418`，无需从服务端日志反推原因。浏览器验收截图保存在 Git 忽略目录 `output/playwright/phase5-failed-report.png`。

## 自动化回归

- 新增接口候选排序测试：模糊帖子列表、精确路径、无匹配稳定回退。
- 新增失败报告测试：无执行记录的规划失败仍生成报告，并保留终止上下文和规划证据。
- `mvn test`：38 个测试套件、88 个测试，失败 0、错误 0、跳过 0。
- 真实 DeepSeek 与 Luminous：模糊目标成功；预期 418 的只读用例按预期失败并生成完整报告。

## 当前边界

- 候选排序降低了同类接口误选概率，不能保证任意自然语言目标都能唯一映射到正确接口。
- 当前 Top-K 会保留多个同业务资源操作，复杂多步骤目标因此仍有上下文；后续若要继续压缩 Tokens，应先建立固定评测集，而不是直接减小 Top-K。
- 旧版本已经失败且未生成报告的历史任务不会自动回填；新链路对之后进入终态的任务生效。
