# ApiPilot 面试讲解提纲

## 一分钟介绍

ApiPilot 是一个面向个人开发者的 API 调用链测试 Agent。用户导入 OpenAPI 并描述测试目标，模型生成结构化步骤，Java 程序负责目录校验、变量依赖、写操作确认、HTTP 执行、断言和审计。失败后只允许有限修正，已经完成的步骤和原有验收条件不能由模型随意修改。

本轮用真实 DeepSeek 对 Luminous 开发沙箱完成了登录、发帖查询和提取错误修复三个固定场景。比较有代表性的结果是：最后一步提取失败后修复一次，前面的创建操作没有重发，数据库独立核验仍只有一条帖子。样本规模很小，不声称通用成功率。

## 为什么不做普通 RAG 问答

需求是“帮我验证 API 业务链路”，最终产物必须是可追踪的请求和可验证的业务结果。检索只帮助模型获得接口与规则证据；难点在于模型提出计划之后，程序如何控制副作用、判断失败、限制修复，以及证明测试真的完成。

与泛化 Agent 的区别要落到实际机制：OpenAPI Operation 白名单、整链变量预检、计划版本确认、不可削弱的断言和写入结果核验。不能声称这些能力为项目独有，也不靠堆更多中间件证明复杂度。

## 关键追问

| 面试问题 | 回答重点 | 证据或边界 |
| --- | --- | --- |
| 为什么用 Java？ | Spring Boot 负责 API 与编排；MySQL 事务持久化任务、确认、审计；执行器用 DTO 与确定性策略隔离模型输出 | 不把提示词当作权限控制 |
| 模型看了文档为什么还猜错字段？ | 之前提示词仅带 `$ref`，缺少对应定义；补全候选接口所需 Schema 闭包，避免盲猜嵌套结构 | 原失败 `authorUsername`，实际 `author.username`；保留失败样本 |
| 如何防止批准旧计划却执行新计划？ | 任务修改次数做 CAS；事务内同时更新计划、运行时引用和确认哈希；客户端提交审阅过的哈希，服务端再校验 | 哈希是版本摘要，不是用户身份或权限令牌 |
| 数据库事务能管住内存和加密存储吗？ | 不能跨介质原子提交；先保存候选上下文，事务提交引用后再切换内存，失败删除候选并保留旧版本 | 恢复以持久化引用为准；不宣称所有崩溃窗口都已验证 |
| 为什么不用模型自己判断是否安全？ | 模型输出是提案；程序独立校验路径、变量、确认状态和网络策略 | 模型填 `dangerousOperationConfirmed` 无法替代服务器授权 |
| 自然语言目标会不会选错接口？ | 会。旧版整串匹配导致候选同分并按路径截断，模糊的“帖子列表”曾选到 `/api/bookmarks`；现在由 Java 按路径、业务词、读写意图和列表/详情形态排序，再交给模型 | 同一目标复测改选 `/api/posts` 并通过；一次 A/B 样本不等于通用准确率 |
| 轻量模式没有 RAG，模型依据是什么？ | 业务文档检索关闭，但 OpenAPI 候选排序与 Schema 引用闭包仍是规划证据；轨迹分别记录文档状态、候选接口和 Schema 数量 | “0 份业务文档”不等于“0 条规划证据” |
| 任务失败后还能审计吗？ | 规划、执行或观察失败都会生成终态报告；没有 HTTP 步骤时也记录阶段、错误码和候选证据，有步骤时再保留脱敏请求响应与失败断言 | 报告失败不能覆盖原始任务错误；旧历史任务不自动回填 |
| 自动修复是否会把错误“修没了”？ | 锁定全部业务断言、接口、步骤数和已成功步骤，提取变量只允许修正路径 | 删除失败提取器也会拒绝；错误断言必须由人处理 |
| 已创建成功但查询失败怎么办？ | 成功步骤保存请求指纹与加密变量引用；重试读取时复用成功结果 | 真实故障场景仅创建一条帖子 |
| 写入超时直接重试不行吗？ | 远端可能已提交，只是响应丢失；任务进入 `NEEDS_REVIEW`，保留 `EXECUTOR_409_003` 和审计证据，禁止自动重放 | 已用真实代理丢弃写响应验证只创建一次；不承诺 exactly-once |
| 重启后如何恢复？ | 过期租约重新领取，按持久化引用恢复原始上下文，复用可信的成功步骤；不确定写入则停止 | 已验证待确认重启、创建成功后查询中断、写响应未保存时崩溃；稳定主密钥是必要条件 |
| 取消是否立即停止？ | 先保存取消意图，在每个步骤和重试前检查；已经发出的请求仍可能完成 | 已验证延迟 GET 时取消，不再执行后续 POST；不声称能回滚外部副作用 |
| 前两步成功才发现第三步缺参数怎么办？ | 发请求前预检整条链，变量必须来自初始输入或前序提取器；禁止覆盖初始预期值 | 测试断言缺失变量时前面写请求发送次数为 0 |
| 为什么删 Redis？ | 原用途只有命名空间展示，没有缓存或队列收益；任务持久化与租约由 MySQL 实现 | 核心模式只需 MySQL，知识库模式才需要 Qdrant、MinIO；尚未拆分构建包 |
| 如何证明完成，而不是信 Agent 的成功状态？ | 用专属夹具，独立按账号查询数据库计数，再读取详情核验业务字段，保存模型与工具轨迹 | 固定三个场景；不是“准确率 100%” |
| 多用户、高并发安全吗？ | 当前定位本机单用户，未完成鉴权和安全隔离，租约不等于成熟分布式调度平台 | 如有平台需求需重新设计执行边界、配额和隔离 |
| 如何证明接口召回不是只靠一次演示？ | 用 3 份 OpenAPI、50 条中文目标、67 个期望 Operation 做固定回归，记录 Top-1、MRR、Recall@3 和 Recall@12 | 最终 Top-1 与 Recall@12 为 100%，Recall@3 为 94.03%；只代表固定数据集 |
| 为什么真实任务成功率只有 50%？ | 六个场景中三个是故意制造的断言失败、写入待核验和缺失变量；它们正确停止才算通过 | Expected Outcome Pass Rate、负向安全停止率和报告生成率均为 100% |

## 面试前必须亲手完成

1. 从控制台跑一遍登录与发帖查询，能指出模型调用、计划确认、Java 执行和独立验收各发生在哪一步。
2. 对照真实证据解释错误提取路径如何修正，以及前两步为什么没有再次发送请求。
3. 阅读 `AgentTaskService`、`AgentPlanRevisionPolicy`、`ScenarioExecutionService`、`WriteExecutionPolicy`，画出正常路径与写入超时路径。
4. 能解释为什么不能靠异常重试保证恰好一次、为什么必须锁定断言、为什么有事务仍存在跨介质一致性问题。
5. 从浏览器选择 `Luminous API 演示`，用同一个模糊目标讲清旧版误选原因、候选排序后的成功结果，以及为什么这仍不代表自然语言映射百分之百正确。
6. 打开预期状态码 418 的失败报告，指出终止阶段、错误码、OpenAPI 依据、实际/预期断言和脱敏请求响应分别解决什么定位问题。

代码可以由工具辅助完成，但面试中要能解释并修改关键实现。仅背介绍不够，也不要把未亲自参与的开发过程描述成独立完成。

## 可用于简历的事实表述

开发基于 Java / Spring Boot 的 API 测试 Agent，将自然语言目标转为 OpenAPI 约束下的多步骤调用；实现计划版本确认、变量依赖预检和有限失败修复，锁定已完成步骤与原有断言；通过真实 DeepSeek 与业务沙箱验证调用链及失败恢复，使用独立业务核验避免重复写入。

详细测试数量、耗时和限制见 [验收记录](core-agent-validation.md)、[第五阶段验收](phase5-agent-quality.md)与[最终回归记录](final-regression.md)。暂不写未经大样本证明的高并发指标、开放域语义准确率或多租户隔离能力。
